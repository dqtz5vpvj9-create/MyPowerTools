# 接收文件与空间管理

接收端以 15 × 1024 × 1024 字节（界面标为 15 MB）为自动下载上限，恰好等于上限的文件仍可自动下载。

- 公屏、网盘及私聊中转：先接收消息元数据。超过上限时显示“待下载”，点按文件领取，成功落盘后才写接收回执。
- 直连：即使发送设备已经受信任，超过上限也必须由接收方确认；旧版直传协议同样需要确认。
- 用户明确选择下载或重试时，不受自动下载上限限制。

文件助手的设置中新增“空间管理”：按实际文件大小排列助手内已下载的附件，显示总占用，勾选文件后确认清理。文字、发送中的文件、发件原件和管理目录外的文件不会被清理；另存到系统下载目录的副本不在本次清理范围。

清理不删除消息、远端内容或历史回执。清理前持久化 `manualDownloadOnly`，因此进程重启、重新同步和私聊轮询都不会自动重新下载。点按原消息可重新领取，但仍需中转内容未失效或来源在线。直连的临时接收批准也会撤销，防止旧批准触发重新下载。

接口：

- `file-transfer.assistant.storage.inspect`：返回 `{files:[{itemId,name,bytes}]}`。
- `file-transfer.assistant.storage.clean`：输入 `{itemIds:[...]}`，返回 `{freedBytes,removed,errors}`。部分删除失败时逐项报告，不把失败计入已释放空间。

Android APK 使用只读 FileProvider URI 和系统安装器，声明 `REQUEST_INSTALL_PACKAGES`。未知来源授权和最终安装确认由系统处理；APK 不再退回通用文件查看器。单独的 split APK 仍由系统判断是否具备可安装的完整包。

## 验证

新增真实 HTTP / TCP 回归用例覆盖阈值两侧及边界、手动下载、接收回执、清理后重启、重新领取、受信任直连仍需确认，以及保护发送原件、活动文件、管理目录外的文件。Android 文件打开测试覆盖 APK MIME 且禁止通用回退。

2026-10-10 在 Pixel 4a（Android 13，开发包 0.2.12 / 14）上通过真实公网中转验收：

- 投递 8,538 字节 APK 和 16,777,216 字节附件。APK 自动接收；16 MB 附件仅出现消息，`bytesDone=0`、无本地路径。点按后完整下载。
- 在空间管理中仅勾选上述两份测试附件，确认清理后，两条消息仍在、下载路径清空、`manualDownloadOnly=true`；已有的其他六份附件未被选中。
- 点按原 APK 消息后重新下载成功，再次打开系统安装器。未授权未知来源，也未实际安装测试 APK；安装器正确展示系统授权提示。
- 截图及设备状态证据保存在临时验收目录 `/mnt/cache/data-cache`，前缀 `mpt-storage-`，按环境规则七天后清理。

自动化验证：Android 文件打开 100 例通过；阈值、清理、HTTP/TCP 和私聊回归组通过；手机与桌面宽度的空间管理交互用例均通过。全量 Core 中两个 CloudWorker 用例因已有 OpenList 占用固定端口失败，不计作通过。

Windows Dev 更新需同时匹配公共运行组件。验收时发现旧安装布局缺少新版 `IBackgroundActivityService`，随后补齐 Core；SSH 会话直接启动还暴露了 Credential Manager 上下文不匹配。开发更新复用上游 `543d014` 的隐藏交互会话派发器，传入 `-NoOpenShell`，不弹出桌面窗口。Windows 验收布局同时保留该上游分支的 Runtime 内存优化，未改动其他工具的源代码。
