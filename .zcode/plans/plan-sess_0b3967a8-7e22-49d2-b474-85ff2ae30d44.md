# Batch-1 实施计划：ServiceManager + ScreenEase 纵向切片 + A3 门禁

权威 checklist：`docs/18-architecture-revision-fast-plan.md` 的「P0：先完成 ScreenEase 纵向切片」「P0：Service UI 双层模型」对应条目，以及 A3 门禁。

## 现场确认结论（已完成，供后续参考）

- 两个并行契约世界：进程内 `MyPowerTools.Abstractions`(ToolSdk, `JsonObject`) ↔ 线协议 `MyPowerTools.Protocol`(gRPC/protobuf)，Runtime 负责映射，无共享 DTO 程序集。
- IPC 模板：Runner 用 `WebApplication` + Kestrel `ListenNamedPipe(Http2)` + gRPC + `HostControlAuthServerInterceptor` + `SingleInstanceGuard`；客户端 `HostControlClient : IDisposable` + `ForEndpoint()` 工厂 + 命名管道 `mypewertools.runner.hostcontrol` + 32 字节 bearer token（`HostControlAuthTokenStore`）。ServiceManager 进程完全照搬这套托管/认证骨架。
- 现有 `IServiceManager`(Platform.Abstractions) 是 OS-service(sc.exe/systemd/launchd) 查询能力，由 `ServiceBroker` 消费——与新 ServiceManager 完全不同，绝不合并。
- **重要更正**：MPT 当前**不构建、不发布、不启动** `ScreenEase.CoreService.exe`。ScreenEase 今天是 **in-proc 模块** `ScreenEase.MyPowerTools.ScreenEaseModule`（通过 Runner 的 HostControl 通道调用 `screenease.*` 命令）。PID 28744 是用户手动拉起的上游 CoreService。因此 ScreenEase→ServiceUnit 是一次**真正的提取迁移**，外加一个薄 adapter 去监督上游 `ScreenEase.CoreService.exe --pipe-only`（pipe `screenease.core`）。
- 工具 Surface 的 host 注入点：`IMptHostContext`（含 `ToolId`），scope 限定靠 Host 注入的 `IServiceUnitClient`。

## 已锁定的关键决策

1. **传输**：ServiceManager 用独立进程、独立 named pipe `mypewertools.servicemanager.v1`、独立 protobuf service、独立认证 token。复用范围仅限 gRPC named-pipe hosting、channel factory、bearer-token interceptor、ACL、错误模型、事件序列等 IPC 基础设施。
2. **装配拆分范围（Batch-1）**：现在只新建 `MyPowerTools.Ipc.Shared`（基础设施）+ `MyPowerTools.ServiceManager.Contracts/Client/Server`（新装配）；现有 HostControl **保持原样**（改为引用 Ipc.Shared），它自己的 Contracts/Client/Server 内部拆分推迟到 Batch-4（P1 依赖拆分，原计划已排）。
3. **scoped `IServiceUnitClient` 放进 `MyPowerTools.Abstractions`(ToolSdk)**，工具已经引用它，由 Host 经 capability/context 注入。

## 步骤总览（连续推进，每步一个可运行闭环）

### 阶段 A — 共享 IPC 基础设施 + 新契约骨架（无运行时行为变更）

**A1. `src/MyPowerTools.Ipc.Shared/`（新装配，net10.0，可打包）**
- 把下列「纯 IPC 基础设施」从 `MyPowerTools.HostControl` 迁入（移动+改名命名空间为 `MyPowerTools.Ipc`）：
  - `IpcChannelFactory`：抽自 `HostControlClient.ForEndpoint` 的 `SocketsHttpHandler`+`GrpcChannel`+命名管道/UDS `ConnectCallback`（`HostControlClient.cs:42-70`）。提供 `ForNamedPipe(string address)` / `ForUnixSocket(string address)` / `ForEndpoint(IpcEndpoint)`。
  - `BearerTokenAuthServerInterceptor`、`BearerTokenAuthClientInterceptor`：把 `HostControlAuthServerInterceptor`/`ClientInterceptor` 泛化为「按 header 名 + token 校验」。
  - `AuthTokenStore`：泛化 `HostControlAuthTokenStore`，参数化 token 文件名（如 `servicemanager.token`）、环境变量。
  - `TokenEquals` 常量时间比较 helper。
- HostControl 原文件改为引用 Ipc.Shared 并以薄包装保持公开 API 不变（`HostControlClient` 仍叫这个名字，工厂不变），避免 Shell/CLI/Test 的 25+ 处调用站点改动。
- 依赖：`Grpc.Net.Client`、`Grpc.Core.Api`、`MyPowerTools.Platform.Abstractions`（拿 `IpcEndpoint`/`PlatformId`）。
- 纯 `src/` 新装配，加入 `MyPowerTools.slnx`。

**A2. ServiceManager 线协议：`proto/mpt_service_manager_v1.proto`（新）**
- `package mypowertools.servicemanager.v1;` `option csharp_namespace = "MyPowerTools.Protocol.ServiceManager.V1";`
- `service ServiceManager`：`ListUnits`、`GetUnit`、`Start`、`Stop`、`Restart`、`Reload`、`TailLogs(stream LogEntry)`、`SubscribeUnitEvents(stream UnitEvent)`。
- 消息：`UnitId`、`UnitSnapshot`(id, tool_id, display_name, state, pid, started_at, uptime, version, autostart, restart_policy, restart_count, last_error, readiness{ok,message}, exit_code)、`UnitSpec`(id, tool_id, exec, arguments, working_directory, environment, autostart, restart_policy{max_restarts,backoff_ms}, readiness{kind,pipe/timeout}, stop_timeout_ms, data_roots, depends_on, instance_token)。
- 枚举 `UnitState { INACTIVE=0; ACTIVATING=1; ACTIVE=2; DEGRADED=3; FAILED=4; DEACTIVATING=5; }`（对齐计划「最小状态机」）。
- `UnitEvent`(seq, unit_id, type, time, payload Struct)，沿用 `seq` 单调游标约定（与 `HostEvent`/`MptModuleEvent` 一致）。
- 错误复用 `MptError`/`MptErrorCodes`；新增 code `SCOPE_DENIED`。
- 在 `MyPowerTools.Protocol.csproj` 加 `<Protobuf Include="..\..\proto\mpt_service_manager_v1.proto" GrpcServices="Both" ProtoRoot="..\..\proto" />`。

**A3. 进程内契约（ToolSdk 侧）：在 `MyPowerTools.Abstractions` 新增**
- `record ServiceUnitSnapshot(...)`、`ServiceUnitManifest(...)`、`ServiceUnitRestartPolicy`、`ServiceUnitReadiness`。
- `enum ServiceUnitState { Inactive, Activating, Active, Degraded, Failed, Deactivating }`。
- `interface IServiceUnitClient`（scoped）：`GetSnapshotAsync`、`SubscribeEventsAsync(EventCursor, CT)`、`StartAsync`、`StopAsync`、`RestartAsync`、`ReloadAsync`、`TailLogsAsync(CT)`、`OpenManagementPageAsync()`。配套 `ServiceUnitEvent`、`EventCursor`（复用现有）。
- `interface IServiceUnitClientFactory`：Host 注入点，`IServiceUnitClient ForTool(string toolId)`。
- 放 Abstractions 是因为工具已经引用它，且 `IMptHostContext` 已有 `ToolId`。Runtime 负责 scoped→administration 的映射与 scope 校验。

**A4. 验证 A：`dotnet build` 整 solution 通过**（HostControl 改为引用 Ipc.Shared 后不能破坏现有调用站点）。第一个 checkpoint。

### 阶段 B — ServiceManager 进程 + 状态机 + 测试 unit（A3 Process Gate 前半）

**B1. `src/MyPowerTools.ServiceManager/`（新可执行装配，net10.0）**
- `Program.cs` 照搬 Runner 托管骨架：`SingleInstanceGuard.Acquire("MyPowerTools.ServiceManager")`、新 `IpcEndpoint.ServiceManagerDefault`、`AuthTokenStore.GetOrCreateToken`、`AddGrpc`+`BearerTokenAuthServerInterceptor`、`ConfigureKestrel.ListenNamedPipe(Http2)`、`MapGrpcService<ServiceManagerGrpcService>()`。
- 接受 `--data-root`（默认 `%LOCALAPPDATA%\MyPowerTools`）、`--deploy-root`（默认 `%LOCALAPPDATA%\MyPowerTools\ServiceManager\<version>`，与 `bin/Debug` 分离）。
- 不引入 tray/hotkey/shell 启动（那是 Runner 的职责）。

**B2. `src/MyPowerTools.ServiceManager.Server/`（新类库）核心引擎**
- `UnitSupervisor`：单一 unit 生命周期。`Process.Start` 启动 exec，**不**使用 `KILL_ON_JOB_CLOSE`（关键：避免 job 对象连带终止——只设进程级，Stop 时显式 `Process.Kill(entireProcessTree:false)` + `stopTimeout` 优雅退出）。维护 PID、StartedAt、RestartCount、LastError、ExitCode。
- 状态机 `UnitState` 转换（inactive→activating→active；失败→failed/degraded；显式 Stop→deactivating→inactive），所有转移发 `UnitEvent` 进 `UnitEventBus`（单调 `seq`，仿 `EventBus.cs`）。
- RestartPolicy：进程非零退出且未达 `MaxRestarts` 时按 `Backoff` 重启。
- **重接管**：启动时读 `state/units/<id>.json`（含 PID + InstanceToken），用 `Process.GetProcessById` 验活，存活则直接 `active` 并接管（不重启）。这是「ServiceManager 重启不杀 unit」的实现核心。
- `UnitLogRouter`：按 tool 分区捕获 stdout/stderr，滚动上限 + 最近错误摘要（仿 `LogRouter.cs`）。
- `ServiceUnitRegistry`：从 deploy-root 读 `unit-manifest.json` 清单，`Reload` 重扫。
- `ServiceManagerGrpcService : ServiceManager.ServiceManagerBase`：实现 A2 全部 RPC，服务端按 `tool_id` 二次 scope 校验（scoped 操作非本工具 unit → `SCOPE_DENIED`）。

**B3. `ServiceManagerAdminClient`（administration，跨工具）放 `src/MyPowerTools.ServiceManager.Client/`**
- sealed `IDisposable`，工厂 `ForDefaultEndpoint()`/`ForEndpoint(IpcEndpoint, string? token)`，照搬 `HostControlClient` channel+interceptor 模式（用 Ipc.Shared）。统一 Services 页面用它。

**B4. Scoped 客户端实现 + Host 注入**
- `MyPowerTools.Runtime` 加 `ScopedServiceUnitClient : IServiceUnitClient`：构造时绑定 `toolId`，所有调用先 scope 校验，底层委托 `ServiceManagerAdminClient`。
- `IServiceUnitClientFactory` 实现：Runner/Shell 启动时按 `ToolId` 注入。
- 新增 `IpcEndpoint.ServiceManagerDefault(PlatformId)`。

**B5. 测试 fixture：`tests/fixtures/test-service-unit/`**
- 极小 .NET 控制台进程：每 1s 写 heartbeat（含 PID）到 stdout 与 `<dataRoot>/heartbeat.txt`，支持 `--pipe <name>` 启最小命名管道 readiness 端点响应 `pong`，CTRL_C 优雅退出。
- 配套 `unit-manifest.json`（autostart=false, restartPolicy max=2, readiness pipe）。

**B6. A3 Process Gate 脚本 `scripts/verify-architecture.ps1 -Tier Process`**
- 唯一测试资源：临时 data root（`$env:TEMP\mpt-a3-<guid>`）、唯一 pipe `mpt-a3-<guid>`、唯一 unit id `test-a3-<guid>`、专用端口。
- 覆盖计划 A3 全部断言：scoped Start→admin 经事件收 active+PID+readiness；重复 Start 同 PID 单实例；断开两客户端后进程存活；**重启 ServiceManager 后 PID 不变（重接管）**；admin Restart→scoped 收新 PID；scoped 访问他工具 unit→`SCOPE_DENIED`；scoped Stop→admin 收 inactive、heartbeat 停止。
- 输出 `artifacts/architecture-smoke/result.json`。清理只终止本次 fixture 进程；不碰用户正在用的 ScreenEase.Service。

**Checkpoint B：`-Tier Process` 全绿。** 此刻 ServiceManager 引擎被一个真实后台进程证明：独立生命周期、双 UI 单一状态源、事件同步、重接管、scope、单实例。

### 阶段 C — ScreenEase 真实纵向切片（用真实 unit 把模型跑穿）

> PID 28744 仅作现场证据；不硬编码、不直接接管、不在开发期终止。现有 in-proc ScreenEase 继续工作，直到新 unit 通过 readiness 后做一次显式受控切换。开发态允许用 settings 指向现有 CoreService artifact；发布态用 package-relative executable。

**C1. `tools/screenease/current-integration/src/ScreenEase.Service/`（新薄 adapter）**
- 由 ServiceManager 监督的可执行：定位并启动 `ScreenEase.CoreService.exe --pipe-only`（env `ScreenEase__Transport=pipe`、`ScreenEase__NamedPipe__Name=screenease.core`、`ScreenEase__Driver=windows`），监督进程，转 pipe 命令为 MPT 命令面。
- `unit-manifest.json`：`exec` 指向 package-relative 路径，`readiness` = pipe `screenease.core` ping（沿用上游 `NamedPipeCommandService`），`dataRoots` 声明 ScreenEase 数据目录。
- 不复制上游源码进父仓库；引用 submodule 内构建产物。

**C2. ScreenEase Surface 接 scoped client**
- 改 `ScreenEaseToolService.cs`：除现有 HostControl 命令调用外，新增经 `IServiceUnitClientFactory.ForTool("screenease")` 拿 scoped client，呈现服务状态（state/PID/uptime/restartCount/readiness）+ 把「开启护眼/关闭护眼」等业务命令映射到 unit Start/Stop/Restart（业务命令与生命周期命令分开注册）。紧凑融入现有标题区/诊断区，不加巨大通用状态栏。

**C3. 统一 Services 页面 `System > Services`**
- 新 Shell 页面，用 `ServiceManagerAdminClient` 跨工具列 units：分组/搜索/状态筛选；每行 工具图标/名称/状态/PID/运行时间/版本/autostart/重启次数/最近错误；操作 Start/Stop/Restart/Enable-Disable autostart/Tail logs/Open tool/详情。
- 事件经 `SubscribeUnitEvents` 流到 Shell（仿 `HostControlEventStreamMonitor`），两入口响应式同步、无轮询。

**C4. ScreenEase 验收闭环（Batch-1 完成定义）**
- Shell 重启期间 ScreenEase Service PID 不变、护眼状态有效。
- Runner 重启期间 PID 不变，Runner 恢复后重订阅 unit 状态。
- solution rebuild 期间 PID 不变（只有部署新 ScreenEase.Service 时受控重启）。
- ScreenEase 工具页与统一 Services 页控制同一 unit；任一入口操作后另一入口经事件自动更新。
- Surface 人为加载失败后，统一 Services 页仍可查日志/重启/确认 readiness。
- 截图：ScreenEase 自定义 Service UI + 统一 Services 页（仅在相关 UI 改动时人工审查）。

## 风险与缓解
- **proto 增量编译**：新 proto 进 Protocol.csproj 触发一次 g Regen；A4 solution build 会捕获映射断裂。
- **重接管竞态**：ServiceManager 启动时若 unit 进程恰好退出，`GetProcessById` 抛 `ArgumentException` → 视为非存活，按 autostart 决定是否拉起；不误判。
- **scope 绕过**：scoped 客户端绝不持原始 admin token；scope 校验在服务端按 `tool_id` 二次校验，客户端仅过滤视图。
- **ScreenEase 双跑**：切换前用 readiness 探测确认新 unit 就绪；旧 in-proc 模块保留为 fallback 直到验收通过。
