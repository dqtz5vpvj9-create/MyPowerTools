## 目标
在 `MyPowerTools.AvaloniaSdk` 里独立实现一份权威的 `MptCommandFaultBoundary`，取代各 Surface 项目里手抄的、互相不一致且含死锁 bug 的 `ShellCommandFaultBoundary` 拷贝。

## 范围
只改 SDK 和 SDK 的用户（Surface 项目）。**不动主 Shell**（本次范围外）。

## 改动清单

### 1. 新增 `src/MyPowerTools.AvaloniaSdk/MptCommandFaultBoundary.cs`
独立的权威实现，参照 SDK 现有风格（`MptAsyncRelayCommand`、`MptObservableViewModel`）。

```csharp
namespace MyPowerTools.AvaloniaSdk;

/// <summary>
/// Fire-and-forget fault boundary for UI command callbacks in dotnet-surface tools.
/// Runs an action on the calling thread without blocking it; async actions are awaited
/// on a continuation that does not require the calling thread, so clipboard and other
/// UI-thread-affine async operations cannot deadlock the UI.
/// Faults are written to Debug listeners; surfaces can observe them through the optional hook.
/// </summary>
public static class MptCommandFaultBoundary
{
    public static void Run(object? source, string operationName, Action action)
    {
        try { action(); }
        catch (Exception ex) { TraceFault(operationName, ex); }
    }

    public static void Run(object? source, string operationName, Func<Task> action)
    {
        // Fire-and-forget: never block the calling (UI) thread. The Task's continuation
        // is scheduled by its awaiter; we do not capture a sync context that would force
        // it back onto a blocked UI thread.
        _ = RunCoreAsync(operationName, action);
    }

    private static async Task RunCoreAsync(string operationName, Func<Task> action)
    {
        try
        {
            await action().ConfigureAwait(true);
        }
        catch (Exception ex)
        {
            TraceFault(operationName, ex);
        }
    }

    /// <summary>Optional observer hook. Surfaces that want to surface faults in-product
    /// subscribe here; default behavior writes to Debug listeners.</summary>
    public static event Action<string, Exception>? FaultObserved;

    private static void TraceFault(string operationName, Exception ex)
    {
        System.Diagnostics.Debug.WriteLine($"[{operationName}] {ex.Message}");
        FaultObserved?.Invoke(operationName, ex);
    }
}
```

**关键安全点**：
- `Run(Func<Task>)` 用 `_ = RunCoreAsync(...)` fire-and-forget —— **绝不在调用线程上 `.GetAwaiter().GetResult()`**（这是 RemoteNotifications.Surface 死锁的根因）
- `RunCoreAsync` 用 `ConfigureAwait(true)` —— 这是对的：Surface 的 UI 命令需要回到 UI 线程完成 UI 更新，但因为 `Run` 本身没有阻塞 UI 线程，continuation 能正常排上 UI 线程（和主 Shell 版完全一致的语义）
- 保留与现有拷贝一致的 `Run(object?, string, Action)` 和 `Run(object?, string, Func<Task>)` 两个重载，调用点签名不用变（只改类名）
- 顺带提供一个 `FaultObserved` 事件 hook（可选），让未来 Surface 想在产品里显示 fault 时有挂载点；不影响当前调用点

## 不改的东西
- **主 Shell 的 `ShellCommandFaultBoundary.cs`** —— 按你的要求，本次只涉及 SDK 和 SDK 用户。主 Shell 那份的 `Run/RunCoreAsync` 虽是死代码、Context/Sink/Identity 虽只被 Shell 内部用，都保持原样。
- **主 Shell 的 `AsyncRelayCommand`** —— 它用的是 Shell 自己的 `ShellCommandFaultBoundary.Report`（不是 Run），不受影响。
- 其他 4 个 Surface（adb-forwarder / doubao / paste-image / smartbird）—— 它们没有本地拷贝，也没调用 `ShellCommandFaultBoundary.Run`，无需改动。

## 为什么这样设计是对的
- **单一权威实现**：以后所有 Surface 共用 SDK 这一份，再也不会出现「抄错成 `.GetAwaiter().GetResult()`」或「抄成 `async void`」的问题
- **符合 SDK 现有模式**：和 `MptAsyncRelayCommand`、`MptObservableViewModel` 同一命名空间、同一 `Mpt` 前缀、同一 `public static` 风格
- **零 API 破坏**：调用点只改类名，签名 `Run(object?, string, Action)` / `Run(object?, string, Func<Task>)` 完全保持
- **根治死锁**：fire-and-forget 语义保证 UI 线程永不阻塞
- **范围最小**：只动 SDK + 2 个 Surface，不碰主 Shell、不碰其他 4 个 Surface
